## What median is defensible now

All eleven USB request widths (including bin quantization) sort as2400,2400,2600,2650,2700,2700,2703.125,2718.75,2718.75,2950,3000. The median is **2700Hz**. This combines verified source UI defaults with existing captured control requests; it is not an eleven-receiver server-executed filter measurement. Vertex2400 and PA3FWM2700 were added from exact frontend evidence below, superseding the earlier nine-receiver subset. Exact matched passband needs both low and high edges, not width alone. A2700Hz width could be0..2700 or300..3000 and will treat low-frequency content differently.

Stream sample-rate known subset: Phantom,Plus,sv1btl,Nova,ka9q,Uber12000; OWRX11025 and OWRX+ inferred11025. Median12000Hz. It is defensible as a subset median only. Browser AudioContext44100/48000 are rendering rates and must remain separate. For OWRX, setting browser context48000 naturally produces stream12000; this also changes browser rendering conditions and must be uniform across products if used.

No all-11 median for FFT size is meaningful: channelizer FFT131072, spectrum FFT4096 and pixel/row bins1024 are different quantities. Define target transmitted bins **per equal RF span**, then use actually received rows at a fixed browser viewport. Source-supported configured minimum row widths (Nova1024,Phantom1024,Plus2048,sv1btl1024,OWRX4096,OWRX+4096,Uber1024) have subset median1024, but this mixes fixed widths and minima and is therefore not a safe measured matching target yet.

Likewise no measured median rows/s: source target rates differ from steady delivery because floor/ceil skip, user-count slowdown, and client divisors. Compute actual row cadence from protocol data after warmup, separating control frames. Theoretical nine-ish source rates are not an acceptable replacement for that measurement.
